# Qwen 3.5 Runtime Delta Audit

Last updated: 2026-07-06

This document records the code and build differences between the pinned upstream
software in the Qwen 3.5 nightly base image and the image used for the current
NeMo-RL Qwen 3.5 work. It is intended to be the source of truth for external
change review.

The audit unit is a built image, not a branch name. Host launchers, checkpoints,
and unbuilt working-tree changes are called out separately because they do not
change the image runtime.

## Runtime Differences

Every source difference introduced by the Dockerfile is listed below. "Required"
means required for the currently observed stack, not approved for permanent
retention.

### D1: Preserve Qwen Tool-Call Reasoning Content

| Field | Value |
| --- | --- |
| Upstream component | NeMo Gym |
| Target | `responses_api_models/vllm_model/app.py` |
| Patch | `docker/gym/qwen35-gym-vllm-model.patch` |
| Size | 7 insertions, 1 deletion |
| Status | Required correctness workaround |

For assistant messages containing tool calls, the patch leaves reasoning text in
`content` instead of moving it to `reasoning_content`. The Qwen 3.5 chat template
otherwise omits that text for structured tool-call history, so rerendered history
is no longer token-contiguous with the sequence generated by the model.

This patch does not create reasoning text, tool calls, rewards, or tokens. It
preserves model-generated content that is already present in the response.

Retire this patch when the pinned Gym model adapter and Qwen 3.5 chat template
preserve the same token sequence without it.

### D2: Use a Shared Apptainer Workspace and Robust Log Creation

| Field | Value |
| --- | --- |
| Upstream component | NeMo Gym |
| Target | `responses_api_agents/swe_agents/app.py` |
| Patch | `docker/gym/nightly-swe-agent-apptainer-logs.patch` |
| Size | 4 insertions, 2 deletions |
| Status | Required platform integration workaround |

The patch makes two filesystem-only changes:

1. Create the Apptainer log directory with `parents=True`.
2. Allow `NEMO_GYM_SWE_WORKSPACE_ROOT` to select a host-visible shared workspace.

It does not alter prompts, model output, grading, or rewards. Retire it when Gym
provides equivalent workspace configuration and parent-directory creation.

### D3: Backfill Failed Gym Rollouts as Zero-Reward Trajectories

| Field | Value |
| --- | --- |
| Upstream component | NeMo-RL |
| Target | `nemo_rl/environments/nemo_gym.py` |
| Patch | `docker/gym/qwen35-nightly-nemo-gym.patch` |
| Size | 119 insertions, 14 deletions |
| Status | **Provisional resilience policy; requires explicit audit approval** |

The patch preserves rollout batch cardinality when a Gym request or response
cannot be postprocessed. It inserts a synthetic two-message fallback trajectory
built from pad or EOS token IDs, sets reward to `0.0`, records a failure reason,
and emits a warning. It also handles malformed `response.output`, non-dictionary
output items, and responses with no generation tokens.

This change cannot give a failed sample a positive reward or fabricate a model
answer. It can, however, turn conditions that previously aborted the run into
zero-reward training samples. That changes failure semantics and may hide a
systematic infrastructure or parsing defect. The current broad `except Exception`
is the highest-priority delta to narrow or remove before an audited benchmark.

The helper does not attach an explicit loss mask to its assistant fallback token.
Do not assume that the trajectory is loss-neutral merely because its reward is
zero: downstream group-relative advantage calculation could still assign a
nonzero advantage. Before release, either prove that every fallback token is
excluded from policy loss or remove this backfill behavior and fail the rollout.

Before retaining it, define which exception classes are recoverable, expose a
counter for every fallback reason, and set a run-failing threshold for fallback
frequency.

### D4: Load Qwen 3.5 Three-Dimensional MoE Expert Exports into vLLM

| Field | Value |
| --- | --- |
| Upstream component | NeMo-RL and vLLM integration |
| Targets | `nemo_rl/models/generation/vllm/vllm_backend.py` plus one new helper module |
| Patch | `docker/gym/nightly-qwen35-moe-refit.patch` |
| Added module | `docker/gym/qwen35-nightly-moe-refit.py` copied as `qwen35_moe_refit.py` |
| Size | 4 insertions, 2 deletions, plus a 239-line helper module |
| Status | Required model-state correctness workaround; high review priority |

The base vLLM loader does not consume the three-dimensional expert tensors
exported for this Qwen 3.5 MoE path. The helper:

1. Recognizes Qwen 3.5 `gate_up_proj` and `down_proj` expert exports.
2. Leaves all ordinary weights on the standard vLLM `load_weights` path.
3. Maps global expert IDs to rank-local expert IDs.
4. Reshapes the exported expert tensors into vLLM's fused `w13_weight` and
   `w2_weight` layouts.
5. Copies only the experts owned by the local expert-parallel rank.
6. Treats streamed refit calls containing only nonlocal pipeline layers as a
   successful no-op.
7. Fails on rank mismatches, missing destinations, source dimensions larger than
   the destination, or a zero-copy result.

This is parameter-loading code, so it needs stronger evidence than a launch
smoke test. Keep tensor-level equivalence tests for both projections and compare
post-refit model outputs against a reference path before release. Retire the
helper when the pinned NeMo-RL/vLLM integration supports this export layout.

The helper currently permits a source dimension smaller than its destination and
copies only the matching prefix. That is valid only if the remaining destination
is intentionally padded and already initialized correctly. Require an explicit
test and rationale for every such shape, or tighten the loader to exact shapes.

### D5: Reconcile Multi-Turn Qwen Token Prefixes

| Field | Value |
| --- | --- |
| Upstream component | NeMo-RL |
| Target | `nemo_rl/models/generation/vllm/vllm_worker_async.py` |
| Patch | `docker/gym/nightly-qwen35-multiturn-prefix.patch` |
| Size | 106 insertions, 1 deletion |
| Status | Required token-accounting correctness workaround |

The patch normalizes message content after vLLM validation, removes Gym's token
bookkeeping fields before chat-template rendering, counts messages after the last
assistant turn, and finds the suffix boundary using EOS delimiters. If the
rerendered template diverges from the exact model prefix, it keeps the original
model-generated prefix and appends only the rerendered suffix.

It does not reveal future messages or add answer content. Its purpose is to keep
training token IDs aligned with the sequence the policy actually generated.
Retire it when upstream has a tokenizer-independent representation that preserves
exact generated prefixes across tool-call turns.

### D6: Separate and Atomically Bind vLLM Ray V2 Ports

| Field | Value |
| --- | --- |
| Upstream component | vLLM in the Ray actor environment |
| Targets | `vllm/v1/executor/ray_executor_v2.py`, `vllm/distributed/device_communicators/shm_broadcast.py` |
| Patch | `docker/gym/vllm-ray-v2-tcpstore-port.patch` |
| Installer | `docker/gym/apply_vllm_ray_v2_tcpstore_patch.sh` |
| Size | 38 insertions, 4 deletions |
| Status | Required distributed-runtime workaround |

NeMo-RL allocates a 100-port window per vLLM engine. The base Ray V2 executor
probed TCPStore and message-queue ports from the same start value, and a queue
could bind a probed port before rank zero created TCPStore. The patch reserves
the lower 64 ports for message queues, the next 32 for TCPStore, and uses ZeroMQ's
atomic `bind_to_random_port` for queue sockets.

This has no model or reward semantics. It depends on a private vLLM helper and
must be revalidated on every vLLM update. Retire it when upstream allocates the
two endpoint classes atomically from non-overlapping ranges.

### Candidate D4 Replacement: Native vLLM MoE Refit

The candidate removes `qwen35_moe_refit.py` and
`nightly-qwen35-moe-refit.patch`, including the 239-line code path that wrote
directly into vLLM's internal fused expert parameters. Instead:

1. `MegatronPolicyWorker` detects Qwen's stacked three-dimensional
   `gate_up_proj` and `down_proj` exports when
   `NRL_REFIT_SPLIT_FUSED_EXPERTS=1`.
2. It emits standard per-expert `gate_proj.weight`, `up_proj.weight`, and
   `down_proj.weight` tensors, keeping names and payloads in the same stream.
3. `VllmInternalWorkerExtension` passes those tensors to the pinned vLLM
   model's public `load_weights` implementation.
4. A small diagnostic fallback retries individual tensors only after a batch
   failure so the rejected name, shape, and dtype are visible.

This is smaller and avoids assumptions about vLLM's private fused tensor layout.
It still changes parameter-export shape and therefore requires tensor-equivalence
and post-refit output checks before release. The split is opt-in and the Qwen
recipe is the only configuration that enables it.

### Candidate D9: Enable TE FlashAttention-2 on `sm_103`

| Field | Value |
| --- | --- |
| Upstream component | TransformerEngine 2.15 |
| Target | `transformer_engine/pytorch/attention/dot_product_attention/utils.py` in generated actor environments |
| Installer | `apply_transformer_engine_sm103_flash_attention_patch` in `nemo_rl/models/policy/workers/patches.py` |
| Size | One compute-capability tuple added to an existing allowlist |
| Status | Required GB300 compatibility workaround |

The pinned TE gate disables FlashAttention-2 for head dimensions above 192 on
all architectures except an explicit allowlist. The candidate adds `(10, 3)` to
that list. It does not alter attention math or select a different backend; it
allows the already-installed FlashAttention implementation on GB300. The Qwen
recipe opts in with `NRL_TE_ENABLE_SM103_FLASH_ATTENTION_PATCH=1`. Each policy
actor locates its actual uv-environment file, applies the exact edit before
model construction, and reloads the utility module if necessary. Actor startup
fails if the exact pinned expression is neither found nor already patched,
avoiding a fuzzy edit on a future TE version or a silent unfused fallback.

### Candidate D10: Correct Async Initialization Ordering

`async_grpo_train` now completes the initial generation refit before starting
background collection. The generation engines are initialized with dummy
weights, so the prior ordering could produce valid-looking but meaningless
rollouts before refit completed. This change delays collection; it does not
alter prompts, sampled tokens, rewards, or training data after the correct
weights are loaded.

### Candidate D11: Distributed Diagnostics and Source Iteration

The Qwen recipe explicitly configures a 60-minute watchdog for both PyTorch's
default process group and Megatron's TP/PP/EP/DP groups, plus NCCL flight-recorder
output under `/logs`. The launcher also requests periodic Ray log synchronization.
These settings improve diagnosis and avoid the pinned 10-minute subgroup timeout;
they do not suppress or retry a failed collective.

The launcher uses the image's baked source by default. For deliberate development
tests, `NRL_SOURCE_OVERLAY=1` overlays the host checkout's `nemo_rl`, `examples`,
and `qwen_35` directories. It deliberately does not overlay dependencies or
`3rdparty`, so the host source must remain compatible with Gym, Bridge,
Megatron-Core, TE, vLLM, and package versions from the image. Audited runs keep
the overlay disabled and use a rebuilt, digest-pinned image.

### Candidate D12: Bound Gym Transient Disconnect Retries

| Field | Value |
| --- | --- |
| Upstream component | NeMo Gym |
| Target | `nemo_gym/server_utils.py` |
| Patch | `docker/gym/nightly-gym-bounded-transient-retries.patch` |
| Size | 9 insertions |
| Status | Required liveness workaround |

The pinned Gym client retries `ServerDisconnectedError` and `ClientOSError`
forever. The patch raises the original exception after
`NEMO_GYM_TRANSIENT_RETRY_SECONDS` (120 seconds by default), allowing NeMo-RL's
explicit rollout-failure policy to run. It does not convert the request into a
success or reward. The 120-second window is independent of the 1200-second
agent and test timeouts; it applies only to a continuously disconnected HTTP
transport.

### Candidate D13: Qwen Async Ordering, Validation Sampling, and MLPerf Logging

| Field | Value |
| --- | --- |
| Upstream component | NeMo-RL |
| Targets | `nemo_rl/algorithms/grpo.py` and `examples/nemo_gym/run_grpo_nemo_gym.py` |
| Patch | `docker/gym/qwen35-nightly-grpo.patch` |
| Size | 125 insertions, 18 deletions across the two pinned nightly files |
| Added module | `nemo_rl/algorithms/mlperf_grpo_logging.py` |
| Added packages | `mlperf-common` at `c02c93c0414071400a10716d9cd5cb8f668b78d4`; `mlperf-logging` at `3d17f6fb6047955159b69d9c2415317f163fbe43` (tag `6.0.0-rc6`) |
| Status | Required Qwen async correctness and benchmark logging integration |

The Dockerfile previously replaced the pinned nightly's entire `grpo.py` with
the older branch file. That widened the delta by thousands of lines and was
incompatible with the nightly API (`SGLangConfig` was one immediate import
failure). The candidate instead applies a guarded patch to the exact pinned
nightly files. It makes four scoped changes:

1. Start async trajectory collection only after the generation engines receive
   the initial policy weights.
2. Preserve the recipe's validation-only `temperature` and `top_p` while leaving
   training generation parameters unchanged.
3. Emit MLPerf init, block, evaluation, tracked-stat, and run-stop events for the
   async GRPO path.
4. Validate the patched driver import at build time without installing Megatron
   in the driver environment; Megatron remains actor-only.

The two MLPerf packages are the only candidate dependency additions to the NGC
base. Both are pinned to the same revisions used by the branch lock file. The
patch rejects MLPerf logging for synchronous GRPO rather than silently emitting
an incomplete event stream.

The audited-image hashes above remain the identity of `a301b30d5`. Candidate
working-tree files must receive new hashes only after they are committed and a
new image is built. The deleted D4 helper and patch remain listed above solely
because they are present in that historical squashfs.

## Minimal-Change Policy

Apply the following release rules:

1. Pin the NGC base by platform digest, not only by tag.
2. Change the base digest in a dedicated commit with no Qwen patch edits.
3. Keep one patch per independently removable behavior.
4. Do not update dependencies in the Qwen layer. If a dependency update is
   unavoidable, pin it explicitly and add it as a separate audited delta.
5. For every new base, run `git apply --reverse --check` for each patch. If the
   patch is already upstream, delete the patch and its Dockerfile stanza.
6. Fail the build when a patch is neither applicable nor already present. Do not
   use fuzzy patching or append code by line number.
7. Do not use `--container-save` artifacts for final audited runs. Rebuild and

8. Record the final OCI digest, source revision label, squashfs SHA-256, embedded
   fingerprint, checkpoint hashes, config hash, and launch command for each run.
9. Treat D3 as an explicit benchmark-policy decision. Report fallback counts and
   fail the run if they exceed the approved threshold.

completed end-to-end benchmark qualification is claimed by this document. A
release candidate must additionally pass:
